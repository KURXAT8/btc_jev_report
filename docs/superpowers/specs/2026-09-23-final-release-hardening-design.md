# BTC Jev 最終版發布前硬化設計

日期：2026-09-23

## 目標

將目前已完成的 BTC Jev 功能收斂為可長期運作的最終版。保留現有 1／3／7 天預測、新聞與官方來源、Binance 公告常駐收集、持續校準、影子預測、郵件與 systemd 行為；本階段只修正發布可靠性、安裝完整性、重啟恢復與可驗證性問題，不新增產品功能或改變預測政策。

完成條件如下：

- 乾淨環境安裝會包含所有執行期相依套件，包含 Binance WebSocket 所需套件。
- 專案路徑含空白或特殊字元時，渲染出的 systemd 單元仍可正確啟動。
- 每個重要持久化流程都有離線測試：資料庫升級、重啟後續跑、模型預算封頂、背景連線中斷與重新連線、郵件重試防重寄。
- 完整測試、編譯、套件建置／安裝、相依性檢查、systemd 靜態檢查全部通過。
- 驗收紀錄清楚區分本機可驗證項目與必須在實機等待排程或預測到期後才能驗證的項目。

## 不變的界線

不改 Jev 模型版本、預測期限、盤整門檻、新聞選取政策、校準採用門檻、每日費用上限、資料保存政策或既有 SQLite 公開資料結構語意。不刪除既有資料，不重寫已凍結預測與郵件，不在測試中使用真實 API key、secret 或寄信帳號。

## 硬化項目

### 依賴與乾淨安裝

將 `websockets` 列入 `pyproject.toml` 的正式 runtime dependencies，版本範圍與 lock 檔一致。以隔離的暫存虛擬環境執行 wheel 建置與安裝，確認安裝後可 import 所有主要模組並可啟動 CLI 的離線命令。測試環境不連線 Binance，也不要求秘密設定。

### systemd 單元與安裝器

維持 render、install、enable 三階段及既有衝突保護。補強含空白路徑的 `WorkingDirectory`、`EnvironmentFile` 與 `ExecStart` 測試，確認七份 unit 都指向同一專案與 `.env`，且檔案權限仍為 0600。以 `systemd-analyze --user verify` 驗證渲染檔；不在受限執行環境中假裝已啟用 user systemd。

對常駐 Binance 服務保留自動重啟、網路等待、秘密不進日誌、私有暫存目錄與低權限執行。若新增檔案系統限制，必須先確認 SQLite WAL、資料目錄與虛擬環境仍可讀寫／執行，並以 unit 測試固定行為。

### 儲存與重啟恢復

以臨時 SQLite 資料庫驗證現行 schema 及從舊版 schema 升級後，預測、結算、校準與每日 token 預留欄位都保留。模擬在快照、模型階段、部分預測或郵件 MIME 已寫入時程序中止，重跑不得改寫已凍結內容，也不得重複計算或重寄。並確認兩個程序透過 WAL 同時寫入時，交易失敗會留下可重試狀態而不破壞資料。

### 模型預算與來源失敗

維持每個 Jev stage 最多三次嘗試、每日最多 15 次，以及發送前的保守 input-token 預留。測試重試、429／5xx、超時、格式錯誤和預算耗盡，確認正式預測與影子預測的失敗邊界互不污染。新聞、官方 RSS、Binance WebSocket 或日曆短暫失敗時，既有 fail-open／品質標記行為必須保持；不把不完整來源當成完整成功。

### 驗收與紀錄

建立最終發布檢查紀錄，至少包含：測試總數與耗時、compileall、pip check、git diff --check、wheel 建置／隔離安裝、systemd-analyze、CLI offline 檢查、資料庫遷移測試，以及實機排程／Binance 連線／真實預測到期結果的未完成項目。所有成功描述都附有命令輸出或測試結果，不以靜態檢查代替服務實際運行。

## 測試策略

先新增會在缺少修正時失敗的測試，再做最小實作修正。單元測試涵蓋路徑渲染、設定與依賴；整合測試涵蓋 SQLite、pipeline、Jev transport、背景來源與郵件狀態；最後在乾淨暫存環境建置及安裝 wheel。完整 `pytest` 必須通過，任何既有失敗都需在驗收紀錄中說明並修正後再結束。

## 風險與限制

本機無法保證外部 user systemd bus、Binance 即時公告流量、TypeSafe 帳戶計費或未來 1／3／7 天預測命中率。這些只能在部署主機透過 `systemctl --user status`、journal、實際帳戶用量及到期結算逐項觀察。最終版不以測試資料宣稱提高命中率。
