## 1. 已確認的需求與設計決策

使用者已確認：

- 個人看盤輔助，關注比特幣未來 3～7 天走勢。
- 資料包含行情、衍生品與新聞。
- 沿用既有專案的定時 Email 模式及郵件設定。
- AI 僅使用 TypeSafe Jev API。
- 每天台北時間 08:00 寄送；07:30 開始準備。
- 採分層分析：Jev 先分類新聞，再結合市場指標判斷 3 天、7 天趨勢。
- 使用繁體中文郵件模板，保存預測並核對成效，具備失敗提示、重試及防重複寄送。
- 增加 Jev Weekly Report，每週回顧預測成效。

本稿為落實上述需求所選的第一版預設：BTCUSDT、Binance 公開行情、三個新聞 feed、固定趨勢門檻、資料保留時間及重試期限；週報併入每週一 08:00 日報。這些是可在審閱時調整的設計選擇，並非使用者已逐項指定。

## 2. 範圍與架構

採 Python 3.11+ CLI、SQLite、HTTPX、Pydantic、feedparser、Jinja2、Python SMTP 與 systemd user timers。實作時鎖定可用且經驗證的依賴版本。

資料流：公開資料 → 資料快照與指標 → Jev 新聞分類 → Jev 趨勢判斷 → 郵件模板 → Gmail SMTP。SQLite 分別記錄資料快照、預測、到期結果及寄送狀態。

| 模組 | 職責 | 邊界 |
| --- | --- | --- |
| config | Jev、郵件、來源、時間與上限設定 | 不在日誌輸出憑證 |
| sources / calendars | 行情、衍生品、RSS、官方事件日曆抓取及正規化 | 回傳數值、來源、事件與取得時間、健康狀態 |
| indicators / context | 指標、歷史百分位、趨勢／波動情境 | 純計算，不呼叫 AI |
| jev | 建立 typed questions、驗證答案及有限重試 | 唯一 AI 供應商介面 |
| forecast | 固定版本的特徵、標籤與兩階段分析 | 不寄信 |
| evaluation | 到期報酬、分類與機率評分 | 不改寫原預測 |
| baselines | 永遠盤整、均勻機率、歷史類別比例、簡單動能 | 只使用截止前資料，和正式預測同時凍結 |
| weekly | 週別樣本、基準比較、遲到結算修訂及週報快照 | 使用已凍結預測與實際結果，不呼叫 AI 評分 |
| render | HTML／純文字與中文分類模板 | 不生成未有依據的原因敘述 |
| mail | Gmail SMTP、Message-ID 與結果分類 | 不重新執行模型 |
| store / pipeline / cli | 原子狀態轉換、排程與操作 | 保證同日期不建立多個正常寄送工作 |

第一版交付為郵件服務與本機預覽，不增加網頁帳號、手機 App、自動下單、即時盤中通知或其他模型。

## 3. 公開資料與時間規則

### 行情與衍生品

- 標的固定 Binance 現貨 BTCUSDT；郵件價格單位標為 USDT。
- 現貨 `/api/v3/klines`：收集至少 120 根已收盤日 K、180 根已收盤 4 小時 K、200 根已收盤 1 小時 K；另取基準與結算需要的 1 分鐘 K。
- 特徵：1／3／7／30 天報酬、20／60 日 SMA、14 日 RSI、20 日對數報酬標準差、最近完整日成交量與前 20 日均量比，以及 4 小時 K 最近 6 根報酬。
- 補充最新完整小時結束的 1／4／24 小時報酬與最近 24 根小時 K 成交量相對前 24 根的變化；顯示該小時截止時間，不能把這些數值稱為 07:30 即時報酬。日 K 以 UTC 邊界為準，07:30 的最新已收盤日 K 可能已距截止時間近一天，明列日 K 截止時間並由小時特徵補足。
- RSI 使用 Wilder 平滑；均線與波動只用已收盤且連續的 K 線。波動採樣本標準差、不年化。啟動所需暖機歷史包含在資料檢查內。
- 衍生品 `/fapi/v1/fundingRate`：最近 7 天已結算資金費率，依實際時間戳處理，不假設永遠每 8 小時結算。
- `/futures/data/openInterestHist`：1 小時未平倉量，取得足夠的 24 小時與 7 天對照點。以 BTC 數量計算部位變化，另外顯示 USDT 名目值，避免把價格上漲誤當作部位增加。
- 請求使用時間窗、分頁、去重、timeout 與有限退避；不需要交易權限。
- Binance 固定為預測與成效結算的主來源；OKX 的 BTC-USDT 現貨僅交叉檢查價格，不混入 Binance K 線、成交量或部位，也不替代基準價／到期價。

每日分析截止時間為 07:30 Asia/Taipei（`as_of`）；07:30～07:40 蒐集資料，07:55 停止模型工作並凍結郵件。

背景資料工作於每小時 05 分與每日 07:25 蒐集 RSS 並保存內容版本；同時處理官方日曆快取，日曆距最近成功取得滿 6 小時才刷新，但 07:25 強制刷新。該工作不呼叫 Jev、不寄信。每日分析只選取在 07:30 前完成存檔的新聞／日曆版本；截止後才看到或取得的修訂留待下次。首次部署若尚無合格新聞快取，當日呈現資料不足，不用事後新聞冒充截止前可見內容。

市場成交／結算時間與新聞發布時間須不晚於 `as_of`；未收盤 K 線排除。日曆的「安排已知時間」須在截止前，事件本身則可以發生在未來。每筆保存 `fetched_at`，所有輸入在 `forecast_created_at` 前取得；新聞與日曆另要求內容版本在 `as_of` 前已取得。歷史行情事後取回不等於當年即時可見資料，正式成效採部署後凍結預測。

現貨基準 P0 為當日 07:29:00～07:29:59.999 的 1 分鐘 K 收盤價，對應時間邊界 07:30。若缺失，不以不同時刻的價格替代。

行情必須完整到預期最後收盤 K；OI 對照點須距預定對照時間不超過 1 小時。最近資金費率若距截止時間超過 12 小時則標示過期。資料非有限數、價格非正數、時間矛盾或缺口一律不以零補值。

K 線 `close_at` 統一為交易所的最後一毫秒時間戳；判定採 `close_at < as_of`。OI 當前點及 24／168 小時對照點，各取不晚於指定目標時間的最近一點，容許落後至多 1 小時，保存實際時間差；不以未來點補對照。若分母為零，變化率回傳缺失。

### 新聞

首版來源：

- CoinDesk：`https://www.coindesk.com/arc/outboundfeeds/rss`
- Cointelegraph：`https://cointelegraph.com/rss`
- Federal Reserve 貨幣政策公告：`https://www.federalreserve.gov/feeds/press_monetary.xml`

使用 feed 提供的標題、可用摘要、發布時間與原文連結；不抓取付費全文。英文標題保留原文，旁邊搭配中文事件分類與影響標籤；不承諾 Jev 逐篇翻譯或生成摘要。原始新聞文字視為資料，不作為操作指令。

候選為近 72 小時加密新聞及近 7 天 Fed 公告。以正規化 URL、內容指紋與標題去重，先篩選 BTC／Bitcoin、加密市場與總經／監管類關鍵詞，所有 Fed 政策公告保留為候選。最多選 20 則（Fed 最多 5 則；其餘在兩個加密來源間交替取最新，單一來源不足時另一來源補位），避免單一來源洗版。每則摘要最多 600 字元並記錄截斷。Jev 以來源 ID 回傳分類，顯示最多 5 則相關事件連結。

跨來源近似標題只標記「可能同事件」，不當作多份獨立證據；數字、否定詞或事件進展不同的報導不得直接合併。內容變更建立新版本，保存 `first_seen_at`、`fetched_at`、發布時間與內容指紋。新聞標記「官方公告／媒體報導」及「只有標題／附摘要」；來源類別是可追溯性資訊，不是已證實的可信機率。

無有效發布時間的內容不送模型。成功讀取但沒有近期文章，屬有效的「沒有新消息」。來源健康以截止前最近一次成功讀取時間判定，允許最近一次請求失敗但快取仍新鮮；成功讀取距截止時間超過 90 分鐘則為過期。來源異常依下節分級，不能把抓取失敗當成沒有新消息。

### 官方事件日曆

來源限定 [Federal Reserve FOMC 日曆](https://www.federalreserve.gov/monetarypolicy/fomccalendars.htm)與 [BLS CPI 發布日曆](https://www.bls.gov/schedule/news_release/cpi.htm)。保存原始來源 URL、內容版本、取得時間、事件日期／時區與精確程度；保留截止時已知的未來 7 天安排，分別標記是否落入 3 天／7 天視窗。

有官方時間時，以 `America/New_York` 處理美國夏令時間再轉 UTC／台北時間。只有會議日期或日期區間時，保存該地全天／多日範圍，標示「時間未公布」；不假定所有 FOMC 項目都是某一時刻的利率決議。日期範圍只要與預測視窗相交即列為「可能落於期間」。

記錄距已知事件的時間；未知精確時間則呈現日期範圍。不取得或猜測市場共識數值，不把事件尚未公布的結果當特徵。解析失敗與「成功解析但期間內無事件」是不同狀態。快取超過 24 小時即過期，日曆缺漏只讓整體品質降為部分缺漏，不阻擋已有必要市場資料的分析。

### 歷史相對位置與市場情境

只使用相同計算方式、單位及採樣時點的歷史值比較，目標回看 90 天。每項輸出必含原值、百分位、實際資料起訖、樣本數與暖機狀態。Binance OI 端點目前只提供最近一個月，較長歷史由本機逐日累積；不得把 30 天或更短資料標成 90 天。

| 特徵 | 比較樣本 |
| --- | --- |
| 日成交量 | 先前完整 UTC 日 K 的 BTC 成交量 |
| 20 日波動 | 每個歷史日按同一 20 日公式計算的波動 |
| OI 24 小時變化 | 每日相同 UTC 小時的 24 小時 BTC 部位變化 |
| 已結算資金費率 | 與當前相同結算間隔的歷史值；間隔由相鄰時間戳計算，未知或不同間隔不混比 |

百分位公式為 `100 × (較小值數 + 0.5 × 相同值數) / n`，比較集合只含當前觀察之前的有效值，排除當前值與未來資料；`n < 30` 回傳缺少，不以 50 或零代替。初版可從既有歷史／快取計算；資料不足是預期暖機狀態，不需在每日截止前大量回補，也不因此讓基本行情判定失敗。

市場情境使用固定、版本化公式：

- 趨勢：P0 > SMA20 > SMA60 為「上行排列」；P0 < SMA20 < SMA60 為「下行排列」；其餘為「混合／無明確排列」。這是描述，不是未來一定漲跌。
- 波動：歷史百分位 <25 為低、25～75 為中、>75 為高；歷史不足為未知。
- 不同時間尺度分別計分；情境在預測時凍結，不能看完結果才重新分組。

### 資料品質與跨來源檢查

OKX 使用公開 `GET /api/v5/market/history-candles`，指定 `instId=BTC-USDT`、`bar=1m`，按時間窗取得與 Binance P0 相同的 07:29 分鐘 K；僅接受 `confirm=1`。單位同為 USDT，時間必須相同，不以現在 ticker 和歷史價格相比。偏差 = `abs(OKX / Binance - 1) × 100%`。

| 品質 | 初版判定 | 行為 |
| --- | --- | --- |
| 完整 | 主來源資料齊全、三個新聞來源均新鮮、兩個官方日曆快取有效、OKX 同分鐘偏差 ≤0.3% | 正常分析 |
| 部分缺漏 | 主來源齊全且至少一個加密新聞來源新鮮，但其他新聞／日曆缺漏過期、OKX 不可用或偏差 >0.3% 且 ≤1% | 保留分析並列出限制，標明部分缺漏 |
| 不足／衝突 | 必要 Binance K 線／基準價／OI／資金費率缺漏過期；兩個加密新聞來源皆過期；或同分鐘跨所偏差 >1% | 停止趨勢推論，寄狀態郵件 |

0.3%／1%／90 分鐘是保守的工程預設，並非已驗證的最佳門檻。跨所價差也可能是真實市場差異，不宣稱已判定哪一方錯；原數值保留，不裁切異常行情、不用插值掩蓋缺口。

資料品質標籤與 Jev 機率分開，禁止任意將模型機率乘上一個「品質分數」。每份快照記錄品質規則版本、原因碼、來源新鮮度、候選／排除新聞數與跨所價差；無法計算的項目顯示缺失，不顯示零。

## 4. Jev 介面與兩階段分析

直接使用 `POST https://api.typesafe.ai/v1/systemone`，Bearer key 僅在伺服器端。第一版預設固定 `jev-1.13.0`，保存 request model 和 response model；若不可用即報錯，不自動換版。

官方 request 是 `state`、`model`、`questions`；Choice 使用 `type: choice`、`instructions`、`criteria`。問題 ID 不參與推論，實際 instructions 必須明寫新聞 ID、時間尺度及判定規則。

第一階段：最多兩批、每批 10 則新聞；分別用 Choice 判斷事件類別，以及對未來 72 小時、168 小時 BTC 的影響（利多、利空、中性、不明），用 Noul 判斷相關性。各題明確引用同一則新聞及適用時間尺度，保留完整機率，不要求短線與波段答案一致，也不將新聞標題視為已驗證事實。

第二階段：一次請求帶入計算完成的指標、歷史相對位置、市場情境、事件日曆、來源時間與對應時間尺度的新聞分類機率／摘要，以兩個 Choice 分別估計 3 天和 7 天結果。「不足／衝突」時停止此階段；「部分缺漏」帶明確缺漏欄位繼續，不讓模型猜填。無近期新聞但 feed 正常可分析，清楚標註「無近期新聞事件」。同一請求內的問題相互獨立，不假設某題能讀取另一題尚未回傳的答案。

程式另提供可核對的文字標籤，例如 P0 高／低於 SMA20、SMA20 高／低於 SMA60、OI 24 小時增／減、最新資金費率正／零／負；同時保留原數值與公式版本。比較、計數、單位轉換、日期排序全由程式執行。Jev 僅處理事件意涵和趨勢判斷，不從大量原始 K 線自行算指標。

對每則候選另問明確的 Choice：文本性質為「已發生事件的報導／未來預測或評論／未經證實的說法／資訊不足」。這是模型的文本分類，不是事實查核結論。第二階段僅帶相關性 Noul ≥0.5 的新聞（保留完整分類機率與排除計數），新聞指令要求忽略文章中的操作要求；含「忽略以上指令」的測試文章不能改變程式規則或請求設定。

Jev 指令使用英文，中文呈現由固定模板完成。模板只敘述實際指標及 Jev 的分類結果；不把指標相關性說成價格變動的因果解釋。

驗證 response question 集合、type、完整選項、有限的 0～1 機率、總和（容許誤差 1e-4）、confidence 範圍及 choice 是否為最大機率選項。錯誤結果不保存為有效預測，也不悄悄重新正規化。

最大機率平手時，接受 Jev 回傳的任一最大選項並保存原 choice；因差距為零，畫面顯示「方向不明確」。評分仍使用該原 choice，不用本機排序覆寫。Noul 只驗證 `type=noul` 與有限的 `noul` 值在 [0,1]，不要求 Choice 的 confidence 欄位。response model 必須等於固定 request model，否則視為無效答案。

每個邏輯請求最多 3 次嘗試、每日最多 9 次 HTTP 嘗試（跨程序持久化計數），每次 45 秒上限；429、529、其他暫時性 5xx 與網路故障才退避重試，遵守 Retry-After 且不超過 07:55。驗證／授權錯誤不重試。每個完整 request JSON 上限 24 KiB；過大時依固定順序減少新聞，不截掉問題規則或數值欄位。

45 秒是整次呼叫的牆鐘上限，不能僅依賴 HTTP 分段讀取 timeout。每次開始前計算截止剩餘時間，呼叫／退避不得跨越截止；截止後才完成的答案不成為當日預測。`forecast_created_at` 在答案驗證完成時取得，兩個時間尺度原子保存，均需早於 07:55。

凍結快照、請求雜湊與批次後，將每個模型階段及每階段最多三次嘗試持久化；重新啟動僅續做未完成階段，成功答案直接沿用。外部 API 不提供本案可依賴的 exactly-once 保證：若回覆成功但尚未存檔便崩潰，重試仍可能再次計費，必須計入原階段與每日上限。若任何非空新聞批次最終失敗，當日改用狀態郵件；不偷偷刪除失敗批次繼續分析。

記錄供應商回傳 usage。上述限制控制請求數與輸入量，並非美元硬上限；實際 API 價格與帳戶額度於真實連線驗收時核對。

## 5. 預測定義與驗證

令 R = 100 × (到期價格 / P0 − 1)。時間尺度從 `as_of` 起算，分別為 72 與 168 小時。

| 結果 | 3 天 R | 7 天 R |
| --- | --- | --- |
| 偏多 | R > +2% | R > +4% |
| 盤整 | −2% ≤ R ≤ +2% | −4% ≤ R ≤ +4% |
| 偏空 | R < −2% | R < −4% |

這些門檻是第一版可檢查的設計預設，並非經最佳化的市場定律。保存 `label_version`（初版 `labels-v1`）及涵蓋問題、特徵、品質、情境與模板的 `rules_version`／設定雜湊；修改只適用未來預測。

到期價格取同一交易所、同一標的在到期 07:30 前一分鐘 K 的收盤價。每日上午工作會結算已到期紀錄；當次未取得該根 K 則保持待結算並在下次補查，不以最新現價代替。

報告列出三類模型機率。最大機率小於 0.55、或前兩名差距小於 0.15 時標示「方向不明確」，保留原分布；這是顯示政策，並不是增加第四個市場結果。Jev confidence 顯示為「模型確定程度」，與命中率分開。

「明確／不明確」只由上述機率政策決定。另報 confidence 高低組時以 0.55 為高組下界，標示為描述性工程分組；不能以 confidence 代替最高方向機率，或混用兩種分組的名稱。

按 3 天／7 天及模型／規則版本分別統計：

- 已結算樣本數、全部有效預測的三分類命中率與混淆矩陣。
- 多分類 Brier score（對三類平方誤差求和後取平均，0～2，越低越好）。
- 高確定度與低確定度分組結果、方向明確的涵蓋率；不得只展示最好的一組。
- 同日期樣本上的四種比較基準，依下節公式在預測當時保存。

每個版本／時間尺度不足 30 筆顯示「樣本不足」；達標後仍呈現樣本數，不把 30 筆或重疊的 3／7 天視窗當成統計有效性的保證。歷史回放僅檢查程式邏輯，正式成效以部署後凍結的預測為準。

### 比較基準與機率可靠度

| 基準 | 預測當時的固定公式 | 用途 |
| --- | --- | --- |
| 永遠盤整 | 盤整機率 1，其餘 0 | 比較命中率及 Brier |
| 均勻機率 | 三類各 1/3 | 比較 Brier，不替平手機率硬選方向 |
| 歷史類別比例 | 同一時間尺度、標籤版本的過去已完成 07:30 價格視窗，最多回看 365 天；`p_k=(count_k+1)/(n+3)` | 比較過去常見結果的機率基準 |
| 簡單動能 | 以最近完整小時收盤價相對 72／168 小時前收盤價的報酬，套用相應 ±2%／±4% 門檻，選中類別機率 1 | 檢查 Jev 是否優於簡單延續規則 |

歷史比例在非暖機時若最大機率平手，固定依「盤整、偏多、偏空」選擇；暖機備援與均勻基準均無 choice，只比較 Brier。此為本機基準規則，不改動 Jev 原 choice。

每天取得 P0 時即保存價格錨點，即使新聞／Jev 失敗也保留；歷史比例的分母取完整價格視窗，不限 Jev 成功日。用於當日基準的歷史視窗，終點價格與取得時間均須早於當日 `as_of`，剛到期但截止後才取回的資料下一次才能使用。歷史樣本不足 30 時，基準回傳均勻機率並標明「歷史不足，均勻備援」，不得假稱已有歷史優勢。

動能缺少指定小時 K 時標為不可用，不換成不同時刻；基準比較使用共同可用樣本並列樣本數。所有基準與正式預測同時凍結，評分後不能重算成更有利的版本；基準機率預設不作 Jev 輸入，避免新增未驗證的機率混合。

週報另對每類原始機率建立固定五區間 `[0,.2)、[.2,.4)、[.4,.6)、[.6,.8)、[.8,1]`，顯示樣本數、平均機率與實際發生率，僅在累積區塊呈現。區間不足 30 筆加註不足；空區間留空。這是描述性可靠度表，不修改機率，Brier 改善也不能單獨證明校準改善。

### 每週 Jev Weekly Report

預設每週一 08:00 與當日日報同封寄送，主旨加上 `Jev Weekly Report`。每週報告以台北時區前一週一 00:00（含）至本週一 00:00（不含）作為統計區間，依預測的 `due_at` 歸週，不依生成或資料補抓時間歸週。區間與資料結算截止時間須印在郵件中。

例如星期日才產生的 7 天預測，當週仍未到期，不算答對或答錯；它會在到期所屬週接受評分。正常每日一筆時，每種時間尺度一週最多 7 筆有效預測；3 天與 7 天分開列出，不合併為 14 筆獨立樣本。

週報內容：

1. 3 天／7 天各自的到期筆數、已結算筆數、正確筆數及命中率（如 `4 / 6，66.7%`），附三分類混淆矩陣。
2. 平均 Brier score 及四種基準比較。均勻機率不報分類命中率；各比較列出共同樣本數，使用相同標籤／時間尺度與已結算結果。
3. 明確／不明確方向兩組的筆數、命中率及涵蓋率；不把低確定度或未寄出的有效預測排除。
4. 按到期日期排列的明細：預測日期、時間尺度、原始三類機率、原始選擇、到期報酬、實際分類與是否命中。
5. 本週、最近 4 個完整週與累積成效並列；模型／規則版本不同則分表，累積統計標示實際涵蓋起訖日期。
6. 分列未產生預測、已到期但缺價格、尚未到期的數量。未產生數以啟用日起的每日預期工作計算，啟用前不算缺漏；零樣本顯示「尚無可評估資料」，不顯示 0% 命中率。
7. 增加資料品質成效：完整／部分缺漏兩組的樣本數、命中率、Brier score，另列因資料不足而跳過的日數、來源失敗與新聞排除數。所有有效預測仍列入主統計，不能因事後品質較差而移除。
8. 在累積區塊呈現市場情境成效與三類機率可靠度表。趨勢、波動各自分組，初版不做大量交叉切片；未知情境也計數，總樣本不得因此縮減。

跨版本比較顯示各自日期與行情環境，不把不同期間的命中率差直接稱為優化效果。同日期對照、時間順序驗證、機率校準與採用規則集中於[研究計畫](../research/2026-09-21-prediction-quality.md)。第一版只保存研究所需原始資料與版本，不額外呼叫候選模型、不自動調權重或校準。

每一份週報在渲染時保存不可變的週別鍵、統計截止時間、樣本 ID／結果版本及彙總快照，SMTP 重試沿用同一份。晚到價格保持原 `due_at` 所屬週，下週另列「歷史週別補正」，不可算入新週命中率或改寫已寄出的報告；更新的累積／四週數字明示已納入補正。

週報由程式依固定公式計算，中文說明使用模板，不要求 Jev 自行評分或額外生成文字。當日日報因 Jev／新聞失敗而只能產生狀態郵件時，只要歷史資料庫可用，仍附上週報；新的結算價格無法取得則列待結算。樣本不足 30 筆的各統計窗加註小樣本，不因此取消週報。

第一個星期一即可以寄出尚無／少量結果的週報。若星期一整個寄送窗口錯過，該週報標為 missed，不在週二另寄；下次週報仍呈現最近四週與必要補正。週報只是預測表現，不呈現未有交易規則、成本與部位設定支持的投資報酬率。

## 6. 郵件與排程

主旨：`[BTC 波段日報] YYYY-MM-DD｜3日：…｜7日：…`；異常時為 `[BTC 波段日報] YYYY-MM-DD｜分析未完成`。

內容順序：截止時間、品質與基準價 → 3／7 天機率 → 指標／歷史相對位置／情境 → 預測期間內官方事件 → 新聞與原文連結 → 到期核對／週報 → 品質明細。明列跨所價差、來源時間、歷史樣本數及缺漏原因。HTML 與純文字內容一致，HTML 對外部文字做 escaping。

排程獨立命名 `btc-jev-prepare`、`btc-jev-deliver`，使用本專案自己的環境、資料庫和 job ID。

另有 `btc-jev-collect-context` 每小時 05 分及 07:25 保存 RSS／日曆快照，執行上限 3 分鐘，過期輪次不追補；不產生模型費用或郵件。

- 07:30 啟動 collect / evaluate / prepare，07:55 凍結結果；timeout、Jev 失敗或資料不完整均可組成狀態郵件。
- 08:00 啟動寄送；正常報告與狀態郵件每天合計最多一封。
- 每週一在同一個工作中附上 Weekly Report，正常分析失敗時亦可隨狀態郵件寄送；不新增第二封信或第二組 SMTP 重試。
- 暫時性 SMTP 失敗最多於 08:05、08:15、08:30 再試，始終沿用原 MIME bytes、Date 與 Message-ID。
- SMTP 可能接受但回覆遺失時標為 `unknown`，不自動重寄；人工 reconcile 才恢復後續處理。
- timers 可 persistent，但入口檢查時段。錯過 07:55 準備期限只建狀態郵件。四個寄送時槽分別允許在該分鐘內 claim 一次（如 08:30:00 ≤ now < 08:31:00），容納 timer 喚醒延遲；08:31 起不開始寄送，已開始的 SMTP 最多執行兩分鐘。此為「08:30 最後一次」的精確定義；其他分鐘及往日報告不補寄。主機未運作時無法保證寄送。
- 寄送入口能在準備工作崩潰時建立狀態郵件；資料庫損毀或 SMTP 無法使用時，只能由本機 status／journal 回報。

以 SQLite 唯一日期鍵、原子 claim 及租約避免手動／排程併發；正常程序重跑不重寄、不重做已成功的模型階段。寄送前寫入 sending，crash 後回復 unknown，避免把未知結果當作未寄送。

`ready` 代表 payload 已凍結，可在 07:55 前提早完成。已 ready 的工作不得因晚到資料、手動 prepare 或版本設定變更而替換。重試狀態在同一分鐘也只可 claim 一次；人工 reconcile 為未寄送僅開放尚未使用的後續時槽。只有租約過期且無活躍送信工作時才將遺留 sending 轉為 unknown，不能把正常執行中的工作誤判為崩潰。

## 7. 設定、保存與操作

`btc_jev/.env` 存放 `TYPESAFE_API_KEY`、`JEV_MODEL`、資料與來源設定。郵件設定透過明確的 `MAIL_ENV_FILE` 讀取，只採用 `GMAIL_ADDRESS`、`GMAIL_APP_PASSWORD`、`RECIPIENT_EMAIL` 三個欄位；本專案環境變數可逐項覆寫。

不 source 整個舊環境檔；不載入 Gemini 欄位；不將舊專案 DATA_DIR、模型設定或程式模組帶入新專案。帳密不寫入資料庫、郵件或請求，也不在規劃時讀出秘密值。

`check-config` 僅顯示設定名稱是否完整。CLI：`collect-context` 保存 RSS／日曆、`collect` 取得市場快照、`prepare`、`preview`、`send --due`、`evaluate`、`status`、`check-config`、`reconcile`、`cleanup`。preview 不連線、不寄信；prepare 不寄信；send 不呼叫模型。

數值特徵、問題版本、模型答案、基準價及結果保存至少 365 天；新聞標題／摘要快照與渲染郵件保存 90 天，之後只保留來源 URL、指紋與分類；詳細寄送記錄保存 90 天，日期防重複鍵持續保留。新聞原文不落地。清理不可刪除未結算預測或待對帳工作所需資料。

價格錨點、比較基準、情境、歷史樣本摘要與日曆快照保存至少 365 天。歷史數值依同一公式滾動保存，無法取得的過去 OI 不補造。新聞移除後，該筆仍可評分但不再宣稱能完整重播當時全部文字輸入。

90 天文字保留規則也涵蓋模型 request/state、快照 JSON、MIME 與日誌內的新聞副本。將可清理文字 blob 與至少 365 天保留的數值／版本／分類分開存放；清理後保留原雜湊及 `text_expired_at`，不把刪除後的資料當成原輸入重算雜湊。週報的數值樣本引用不延長新聞文字保存期限，未結算或待對帳所必需的資料除外。

週報統計快照與樣本索引保存至少 365 天；每份資料的保留期限不得早於最新引用它的週報所需保留期限。若更早歷史已清除，累積成效必須標為「保留期間累積」，不可標為自啟用起的完整成效。

## 8. 驗收與落地順序

後續實作計畫應依「資料與配置 → 特徵與 Jev → 預測結算 → 郵件與狀態機 → 排程與整合驗收」展開，以下是每階段必要證據：

1. 固定資料驗證特徵、時區、已收盤判定、缺口與趨勢門檻邊界，包含 RSI 的零漲／零跌情形。
2. API fixtures 驗證本案使用的 Choice／Noul、錯誤回應、機率檢查、重試上限、版本紀錄與新聞 ID 對應；網路請求不包含 mail／Gemini 秘密。
3. 時間注入驗證資料截止時間、72／168 小時標籤、待結算補查、不可變原預測及基準比較樣本一致。
4. 本機 SMTP 驗證 HTML／文字、重試、未知結果、併發與程序重啟防重寄；測試不寄到真實收件人。
